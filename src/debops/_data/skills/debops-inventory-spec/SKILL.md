# The DebOps inventory file specification

An *inventory specification* is a YAML document describing the desired state
of files in a project's (or view's) `inventory/` directory. It is applied by
`debops project init`, `debops project refresh`, and `debops project mkview`
via `--template <spec>`. It is the safe way to create or modify inventory
contents without hand-editing generated files.

> **Important**: always apply a spec with `--dry-run` first to review the
> changes. Specs which change existing files need `--force`. Specs are
> confined to the `inventory/` directory — absolute paths, `~`, and `..` are
> rejected.

## Document structure

```yaml
---
# Optional; omitted means version 0 (literal contents)
version: 0

# Required: the files and directories to manage. Each key is a path relative
# to the inventory/ directory.
files:

  # A file with literal contents (a YAML literal block keeps the trailing
  # newline; a plain scalar has none)
  group_vars/all/nginx.yml: |
    ---
    nginx__enabled: true

  # A null value removes the path (a directory, recursively)
  group_vars/all/oldrole.yml: null

  # A trailing slash marks a directory; an empty value makes sure it exists
  host_vars/: ''

# Optional: paths this spec must not remove or clear (wildcards allowed)
keep:
  - 'group_vars/all/keyring.yml'
```

Rules for `files:`:

- Keys are paths relative to `inventory/`; a trailing `/` means a directory.
- A string value writes the file with exactly that content.
- `null` removes the path; a pre-existing file written by the user is only
  replaced or removed with `--force`.
- Files previously generated by DebOps are tracked, so a later spec can
  update them safely.

## Versions

| Version | Meaning |
|---------|---------|
| 0 (or omitted) | contents are written literally |
| 1+ | the document is rendered as Jinja2 first; higher versions gate the `pipe()` and `include()` globals |

Templated specs can compute contents, for example reading the project path
from the environment. The `pipe()` (run a command) and `include()` (read a
file) globals reach outside the specification, so they only work when the
operator passes `--allow-io`.

## Applying a spec

```shell
# Review first — simulate without writing anything
debops project refresh --template myspec.yml --dry-run

# Apply; overwrite or remove existing files when needed
debops project refresh --template myspec.yml --force

# Built-in templates: hosts, local, clear, sshkeys
debops project init --template hosts myproject

# Inspect the result without changing anything
debops project refresh --graph        # inventory graph
debops project refresh --list         # inventory as JSON
```

Multiple `--template` options apply in order; later specs can build on files
written by earlier ones.

## Anti-patterns

- **Skipping `--dry-run`** on anything but a trivial addition.
- **Removing instead of keeping**: if a file should survive, put it in `keep:`
  — a spec that clears `group_vars/` without `keep` destroys hand-written
  variables.
- **Using `pipe()`/`include()` in shared templates** without documenting that
  they require `--allow-io`.
- **Paths outside the inventory**: impossible by design — the confinement
  rejects them; do not try to work around it with symlinks (also rejected).
